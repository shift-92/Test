# Common: снимки и история изменений заявки

`Common` — библиотека C# для работы с заявкой как с редактируемым снимком данных. Она отвечает на два вопроса: какие операции нужны для команды пользователя и каким станет снимок после их применения. Например, при удалении виртуальной машины библиотека определяет, какие связанные строки тоже пометить удалёнными. Она не удаляет записи из SQL Server: чтение предметных данных, хранение снимков и транзакции выполняет `Back`.

## Стек и границы

- `Common.csproj`: `Microsoft.NET.Sdk`, `net10.0`, включены nullable-аннотации и implicit usings. В файле проекта нет `PackageReference` или `ProjectReference`.
- Сериализация — `System.Text.Json`; схема моделей строится через `System.Reflection` и атрибуты. EF Core, ASP.NET Core и MudBlazor не нужны движку.
- `Back` и `Front` напрямую ссылаются на `Common`. `UniversalTables` не ссылается на него: команды таблиц в команды заявки переводит адаптер во `Front`. В частности, `EntityKey` таблицы и `Common.Ticket.Models.EntityKey` — разные типы.

## Модель данных и формат хранения

`EditorState.Entities` — словарь по `EntityKey(Type, Id)`. `Type` — стабильное имя из `[HistoryType]`, а не имя CLR-класса. `EntityState` содержит ключ, `IsDeleted` и словарь `Properties` со значениями `JsonElement`. Снимок плоский: в нём хранится, например, `ClusterId`, а не вложенный объект `Cluster`.

`StateJson.Serialize` записывает **массив строк**, отсортированный по типу и идентификатору. `FromRows` копирует строки и отклоняет повторяющиеся ключи. Для команд, значений и действий используется `ChangeJson.Options` (`JsonSerializerDefaults.Web`, строковая сериализация enum). Имена ключей в `Properties` берутся из CLR-свойств и чувствительны к регистру: например, `Name`, не `name`.

## Путь одной правки

1. При создании заявки `Back.Controllers.TicketController` загружает ИТ-систему и связанные строки, вызывает `FlatMapper.Capture` и `HistoryEngine.Validate`. Один снимок записывается и в `OriginalJson` (база истории), и в `CurrentJson` (текущее состояние).
2. `Front.Tickets.TicketEditor` переводит редактирование ячейки в `Patch.Set` и отправляет `ChangeCommand` на `POST /api/ticket/{id}/commands`. `ActionId` идентифицирует действие; `ExpectedSequence` — номер последнего действия, известного клиенту.
3. Под блокировкой заявки сервер проверяет версию и уникальность `ActionId`. `CommandPlanner.Plan` строит список операций, затем `HistoryEngine.Apply` применяет их **к копии** текущего состояния. После выполнения всего набора движок проверяет схему строк и ссылки и возвращает `ApplyResult`: новый снимок и обратные операции уже в порядке отмены.
4. В одной транзакции сервер обновляет `CurrentJson`, увеличивает `LastSequence` и записывает `StoredAction` с прямыми и обратными операциями и группами удаления. Предметные таблицы ВМ, дисков и т. п. этим запросом не меняются. История статусов заявки хранится отдельно от истории правок снимка.
5. Клиент перечитывает снимок. При HTTP 409 он ищет свой `ActionId` в свежей истории, а не повторяет команду вслепую. `Front.Tickets.TicketSession` строит строки таблиц и сравнивает текущие значения с исходными для подсветки изменений.

## Команды и важные различия

| `ChangeCommand.Kind` | Поведение |
|---|---|
| `patch` | Добавляет целую строку (`Patch.Add`) или заменяет скалярное поле (`Patch.Set`). Это ограниченный набор операций, не произвольный JSON Patch. Путь поля: `/entities/{type}/{guid}/properties/{property}`. Прямое изменение `/deleted` клиентским `patch` запрещено. |
| `delete`, `deleteMany` | По входящим внутренним ссылкам планируется мягкое удаление. `Cascade` расширяет группу, `SetNull` очищает ссылку у остающейся строки, `Restrict` блокирует удаление при наличии такой ссылки. Пересекающиеся каскады объединяются в одну `DeletionGroup`. |
| `restore`, `restoreMany` | По исходному снимку и полной истории определяется активная группа удаления выбранной строки. У ещё удалённых участников группы снимается флаг; ранее очищенные `SetNull`-ссылки эта команда **не** восстанавливает. |
| `rollback` | Чтобы вернуться к `TargetSequence`, планировщик берёт `InverseOperations` более поздних действий от новых к старым. Это **новое действие**, не обрезка журнала. Обратная операция для добавления строки помечает её удалённой, а не стирает ключ. |

Например, в моделях `Back` удаление кластера обнуляет `DbVm.ClusterId`, но оставляет ВМ активной. Восстановление кластера само по себе не привяжет ВМ обратно. Если нужен откат удаления вместе со сбросом ссылки, это сценарий `rollback`, а не `restore`.

Текущая версия схемы команд и действий — `1`. Для воспроизведения нужна история одной заявки с непрерывными `Sequence` от `1`; для восстановления и отката планировщик дополнительно требует историю до текущего `head`. Пустой итоговый план отклоняется. Лимиты планировщика: до 10 000 операций, до 1 000 ключей в `Entities`, непустой заголовок до 500 символов. Неверная команда и устаревший `ExpectedSequence` — разные ошибки (`ChangeValidationException` и `SequenceConflictException`).

## Что проверить при изменениях

- **Новая модель.** Реализовать `ITicketModel`, задать уникальный `[HistoryType("…")]`, публичные `Guid Id { get; set; }` и конструктор без параметров. Сервер сканирует сборку `DbItSystem`. Регистрация типа не загружает данные автоматически: проверить выборку в `TicketController.Create` и отображение во `Front`.
- **Новое поле или ссылка.** Публичное скалярное свойство с `get/set` входит в схему. Для исключения есть `[HistoryIgnore]`. Внутренний FK `Guid`/`Guid?` связывается с навигацией через `[MainObject(nameof(...))]`; по умолчанию действует `Restrict`, для `SetNull` нужен `Guid?`. `[ExternalReference]` оставляет FK в свойствах, но не требует целевой строки в снимке и не допускает поведения удаления. Пример — `DbVm.UsageId`.
- **Совместимость.** `ValidateRow` требует точного набора полей. Даже добавление nullable-поля меняет схему: старый снимок, в котором ключ отсутствует, не равен снимку с явным `null`. Перед изменением имени типа, свойства или формата значения проверить сохранённые `OriginalJson`, `CurrentJson`, пути прямых и обратных операций и воспроизведение истории.
- **Граница UI.** Возможности движка шире текущего `TicketEditor`: адаптер принимает правки для `vm`, `cluster`, `networkRule` и только одношаговые пути полей. Если правка отклонена до HTTP-запроса, проверить адаптер, а не серверный планировщик.
- **Навигация по решению.** От корня решения: реальные модели и правила связей — `Back/DataContext.cs`; API и транзакции — `Back/Controllers/TicketController.cs`; отправка команд и отображение снимка — `Front/Tickets/TicketEditor.cs` и `Front/Tickets/TicketSession.cs`.

Правило работы в этом репозитории: не запускать команды терминала, сборку или тесты самостоятельно. Пользователь компилирует решение вручную в Visual Studio 2026.
